# 渠道评分、故障避让与恢复

本说明对应本次渠道调度完善，尚未随 beta.10 发布。项目能力概览统一维护在 [项目优势与能力说明](project-strengths.md)。

## 选路顺序

请求先检查用户与 Key 权限、分组、模型与协议能力、凭据状态和并发约束，再在合法候选中做调度。渠道优先级数值越大越先尝试；同一层按配置权重与质量评分抽样，失败后沿既有请求计划降级，不重复尝试已经排除的候选。评分不更改实际计费分组、模型价卡或预留资金。

调度区分四类信号：明确禁用、权限或额度不可用的目标不进入候选；硬熔断目标在冷却期内排除；短暂失败采用有兜底的软避让；其余候选按健康与可选上游价值倍率降权。软避让不能绕过硬熔断和凭据停用。

## 真实请求驱动的健康评分

健康反馈覆盖模型调用链路，以 Relay 已确定的结果为准。客户端参数错误与本地终止的那次尝试不惩罚上游，先前真实发生的上游失败仍独立保留；流式请求只有逻辑完成后才记成功，下游放弃读取不记上游失败。异步视频任务提交或轮询只记录对应操作的结果，不把任务执行时长伪装成一次 HTTP 请求延迟。

渠道和凭据分别记录全局状态及模型状态。模型名使用 canonical 路由名的 SHA-256 摘要构造键，保持大小写身份，不在 Redis 键或 Debug 输出中暴露原名。模型不支持、协议不匹配及模型级 429 只影响该模型；认证故障按真实密钥的共享身份处理，配额和账号级限流按实际逻辑凭据处理。连接和服务端错误同时进入全局与模型维度；读取时惩罚取最大值，样本优先使用本模型数据，避免重复计算同一次失败。

| 参数 | 默认值与含义 |
| --- | --- |
| 失败惩罚半衰期 | 10 分钟，无新故障时自动减轻影响 |
| 近期样本半衰期 | 30 分钟，旧成功与失败逐渐失去权重 |
| 样本置信度 | 12 个有效样本前渐进应用成功率影响 |
| 成功率平滑 | Beta(1,1) 先验，避免少量样本给出极端结论 |
| 延迟 EMA | Relay 观测到的成功尝试耗时，alpha = 0.3；不是固定长度窗口或首 token 延迟 |
| 延迟惩罚 | 超过 2.5 秒逐渐降低倍率，30 秒窗口内最多扣 35% |
| 健康倍率下限 | 8%，仅对未硬熔断的候选保留抽样票 |
| 状态过期 | 最近一次反馈后 24 小时；长期不用的状态自动清理 |

基础抽样票为 `配置权重 + 10`。健康倍率结合 `1 / (1 + 失败惩罚)`、近期失败率与样本置信度、延迟倍率计算，使用有界定点整数。成功会将惩罚更新为 `max(0, penalty × 0.2 - 0.3)` 并清除软避让与熔断层级；近期失败样本保留并逐步衰减，避免一次成功直接抹掉长期不稳定的记录。没有历史样本时保持中性。

延迟采用现有 Relay 观测边界：普通对话流完成时更新为最终耗时，其他端点可能在取得成功响应时记录。长输出、多模态任务与普通短对话的耗时不同，因此优先使用本模型质量，不能将该指标当作提供商的固定性能基准。延迟历史也会随空闲时间向中性基线衰减，避免很久以前的慢请求持续压低新流量。

## 短暂失败避让与硬熔断

网络、5xx、过载和限流等瞬时故障触发短期 Fibonacci 避让：15、15、30、45、75 秒继续递增，最长 5 分钟。同一软避让窗口内的并发迟到失败仍增加惩罚，但不会连续拉长退避。超过瞬时故障窗口后重新开始，成功立即清除。

同优先级层存在未软避让候选时先选择这些候选；全部候选均处于软避让时，仍允许按降权后的抽样票尝试，避免普通短错误让整个层没有候选。请求次数和是否允许重试仍由既有 Relay 执行策略限制。

5 分钟窗口内连续 3 次瞬时失败触发硬熔断，冷却依次为 1 分钟、5 分钟、30 分钟。硬熔断不能被“全部候选软避让”的兜底绕过；冷却中的并发迟到失败不升级熔断层。冷却结束后重新接受受限请求，成功后恢复，持续失败则继续降权或升级冷却。

## 上游价值信号

上游价值评分是可选配置，默认关闭（没有信号即倍率为 1）。只在同分组、同 canonical 模型、同优先级且计量单位可比的候选之间比较。成本和近期使用量越低越优，可用上游余额越高越优；每项倍率为 0.5～1.5，再按成本 40%、余额 30%、使用量 30% 合成。

某项少于两个可比候选、候选缺少该信号、所有值相同或单位不同时，该项保持中性。不把零成本当作“未知成本”，也不会用平台售价、用户钱包余额或用户调用额度补全信号。数据由管理员明确提供并维护，不自动宣称支持所有上游平台的余额和成本查询。

仅 weighted 渠道策略使用价值倍率，固定顺序与轮询保持原有语义。健康倍率、授权、并发和计费约束继续生效。

### 管理员配置示例

在渠道的高级 JSON 设置或管理员渠道写入 API 的 `settings` 对象中加入以下字段，保留其他已有设置：

```json
{
  "upstream_routing": {
    "models": {
      "gpt-6.1-sol": {
        "unit_cost": { "value_micros": 500000, "unit": "usd_per_1m_tokens" },
        "available_balance": { "value_micros": 9000000, "unit": "usd" },
        "recent_usage": { "requests": 12, "window_seconds": 300 }
      }
    }
  }
}
```

示例表示该模型单位上游成本为 0.5 USD/百万 tokens、上游可用余额 9 USD、最近 300 秒观察到 12 次请求。成本与余额使用各自的单位，只有完全相同单位的同类字段才比较；不自动换算货币。用量只有相同 `window_seconds` 才比较。移除某项即可停用该项信号，移除 `upstream_routing` 即恢复中性价值倍率。

成本、余额和用量值均为非负整数，最大 `10^15`；用量窗口为 1～604800 秒；单位最长 64 字节，只接受小写字母、数字和下划线；最多 64 个 canonical 模型，整体配置最多 64 KiB。未知字段、负数或小数被拒绝。零成本是一个有效的明确数值，不会导致除零。

这些是管理员维护的观察快照，当前不自动刷新或自动过期。上游价卡、余额或观察窗口变化后应同步更新；无法保证数据新鲜时应移除该信号。价格优先的用户路由仍读取业务价卡，不读取这里的成本值。

## 多节点与升级

健康计数、半衰减、EMA、Fibonacci 与熔断在同一 Redis 服务端时间下原子更新，节点共享结果。读取失败按既有请求规划错误处理；反馈写入失败不覆盖已经确定的业务响应，但会产生脱敏告警。未配置 Redis 时不启用该套运行时质量统计；配置权重和显式上游价值配置仍可使用。

旧版本只含惩罚/熔断的 Redis 状态可按缺少样本读取，首次反馈补齐新字段。部分损坏的字段被拒绝。部署时仍按 [多节点部署](multi-node-deployment.md) 保持节点版本一致；不要依赖新旧版本同时写入时保留完整质量历史。

`pool_mode` 继续把渠道级账号健康管理交给外部池：不新增渠道反馈，不使用遗留渠道惩罚；本地凭据身份与必要的认证隔离仍遵循既有规则。健康评分不修改管理员的永久启停状态。
