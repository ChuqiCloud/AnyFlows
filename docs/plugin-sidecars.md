# 插件安装与运维

本文面向部署 AnyFlows 的管理员。编写插件请看[插件开发](plugin-development.md)，包格式和协议字段见[插件协议参考](plugin-protocol-reference.md)。

## 安装前确认

- 插件包适用于服务节点的操作系统和 CPU 架构，所需解释器、动态库已经安装。
- 服务账号能读写、执行插件缓存目录；默认是运行目录下的 `data/plugins`。
- 插件来自你信任的开发者。未签名插件可以安装，签名也不代表代码经过审核。

目前上传后可直接接入现有页面的是模型资料目录：`catalog.models.read`、`catalog.models.search` v1。它们在登录后的模型页展示资料，不会创建模型调用渠道、价格或调用权限。其他模块需要先在宿主代码中接入，不能仅靠清单声明生效，详见[支持范围](plugin-development.md#支持范围)。

## 上传并启用

1. 使用管理员账号进入“插件管理”。
2. 选择 `.afplugin` 或 `.zip` 文件。
3. 插件需要配置时，展开“可选配置”，按开发者说明填写 JSON 对象；不需要时保留 `{}`。
4. 点击“安装并启用”，再检查“节点运行状态”。

常规安装不需要填写摘要、公钥或签名，也不需要单独批准。安装器会检查包内容和配置，保存归档，启动本节点插件。成功响应表示本节点已通过启动握手和健康检查；其他节点会随后获取部署。

配置会保存到数据库并发送给插件，适合填写语言、显示数量等公开参数。不要填写密码、访问令牌、Cookie 或其他凭据。

上传上限为 **128 MiB**，展开上限为 **512 MiB**，最多 **100,000 个条目**。包内的链接、重复路径、大小写冲突、越界路径等会被拒绝。手工制作的包也必须符合[包格式](plugin-protocol-reference.md#包格式)。

如果显示“需要授权能力”，包已经登记，但没有通过本次上传启用。展开“高级管理”，选择该制品的能力和配置后部署。这个操作只授予调用权限；插件是否出现在某个业务模块，取决于宿主是否已经接入该能力。

需要修改缓存位置时，在服务配置中填写运行目录下的相对路径：

```toml
[server]
plugin_artifact_directory = "data/plugins"
```

系统不提供插件市场或 URL 安装入口。取得插件包后，通过上传安装。

## 升级、回滚和移除

“制品”指某个具体插件包，“部署”指当前选用的包、配置、能力授权和启停状态。每次部署变更都会生成新的 `generation`，用于处理并发修改。

| 操作 | 用途 | 文件和历史如何处理 |
| --- | --- | --- |
| 升级 | 上传相同插件 ID 的新版本并启用 | 保留旧制品和部署历史 |
| 停用 | 暂时停止调用 | 保留包、配置和历史，可重新部署 |
| 回滚 | 选择历史部署恢复 | 将历史包、配置和授权写成一个新代次；目标制品必须仍可用 |
| 卸载 | 停止部署并清理各节点缓存 | 保留数据库归档、制品记录和审计，仍可按规则重新部署 |
| 撤销制品 | 禁止某个包继续使用 | 停用使用该制品的当前部署；该制品不能再次启用 |
| 清理制品 | 释放已撤销包的归档和缓存空间 | 保留元数据、历史和审计；同一制品不能靠重传恢复 |

修改插件代码、清单或资源后，应发布新版本。不要覆盖已经登记的包。并发操作出现冲突时，先刷新当前状态，再重试。

“清理制品”需要满足两个条件：制品已撤销，且没有启用部署引用它。卸载或清理时，在线节点立即或在下次协调时处理；离线节点恢复后继续处理。高级管理手工登记的任意本地目录不会被系统递归删除。

上传后本节点启动失败时，已保存的共享部署可能仍保持启用，其他节点和后续协调可以继续恢复。先查看逐节点错误，不要用反复上传代替故障排查。

## 多节点部署

通过上传安装的插件包保存在共享数据库中，节点自行获取并校验，无需手工复制目录，也无需额外部署对象存储。生产多节点部署仍应按[多节点部署说明](multi-node-deployment.md)使用共享 PostgreSQL 或 MySQL 及 Redis。

各节点需要运行兼容的 AnyFlows 版本，并具备相同插件所需的操作系统、架构和运行依赖。当前不会为不同架构的节点自动选择不同包。发布者公钥配置也应保持一致。

服务启动时恢复部署，之后每 **30 秒**协调一次。缺少或损坏的受控缓存会从归档重新恢复。旧版或高级手工登记的本地制品可能没有共享归档；需要自动分发时，应重新上传对应安装包。

在“节点运行状态”中检查：

| 显示内容 | 判断方法 |
| --- | --- |
| 部署已启用 | 管理员希望它运行，尚不能说明节点已经启动 |
| 待就绪、下载中、启动中 | 节点尚未完成恢复或启动 |
| 就绪 | 节点租约有效、代次和摘要匹配，进程状态为 `ready` |
| 失败 | 查看固定错误码和该节点的运行依赖 |
| 过期 | 节点或插件观察超过 **120 秒**未更新，不计入就绪数量 |

服务重启会产生新的节点实例标识，旧记录会过期。系统 `/readyz` 也不能代替插件逐节点状态。

## 选择隔离策略

隔离策略由服务配置决定，插件不能自行降低：

```toml
[server]
plugin_isolation = "auto"
```

| 策略 | 适用情况 | 行为 |
| --- | --- | --- |
| `auto`，默认 | 常规部署 | Linux 有可信 `setpriv`、`prlimit` 时启用资源限制，缺少时采用普通进程；Windows 使用 Job Object 清理进程树 |
| `trusted` | 明确信任插件代码 | 按服务账号权限运行，仍保留进程清理 |
| `restricted` | Linux，需要固定资源上限 | 必须具备上述工具；限制地址空间和累计 CPU 时间 |
| `require_sandbox` | Linux，需要文件系统和网络隔离 | 还需 Bubblewrap 和内核命名空间支持；插件无法直接访问外网 |

`restricted`、`require_sandbox` 在不支持的平台或缺少系统能力时启动失败，不会降级。Windows Job Object 负责进程树管理，不提供文件系统或网络沙箱。各策略的具体限制见[隔离参数](plugin-protocol-reference.md#隔离参数)。

控制台顶层的 `isolation` 是配置策略；各插件节点记录的 `isolation` 才是实际运行等级。

## 可选签名与官方标识

自己的插件可以不签名。需要核验发布者时，在服务配置中登记其 **Ed25519 公钥**：

```toml
[[server.plugin_trusted_signers]]
key_id = "publisher-example"
public_key_base64 = "<Base64 编码的 32 字节公钥>"
```

官方来源使用独立配置：

```toml
[[server.plugin_official_signers]]
key_id = "official-publisher"
public_key_base64 = "<官方发布者提供的 Base64 公钥>"
```

两个列表默认均为空。只有完整签名通过对应公钥验证，才能显示“签名已验证”或“官方插件”。插件名、ID 前缀和签名者 ID 都不能代替验证。普通受信发布者也不会因此变成官方来源。

未配置的签名者按未验证来源处理；如果签名者命中已配置公钥，但签名无效，安装会失败。签名不额外授予业务能力，也不改变隔离策略。制作签名包见[签名格式](plugin-protocol-reference.md#可选签名)。

## 常见问题

| 现象 | 先检查什么 |
| --- | --- |
| 包被拒绝 | 文件是否为受支持的 ZIP，入口是否在 `payload/` 内，路径是否重复或越界，大小是否超限 |
| 配置无效 | 是否为 JSON 对象、是否符合清单 Schema、是否包含敏感字段 |
| 需要授权能力 | 到高级管理选择能力后部署；确认宿主已有对应业务入口 |
| `startup_failed` | 入口能否执行、架构是否匹配、解释器和动态库是否齐全、是否误把日志写到标准输出 |
| 开启强隔离后无法启动 | 工具和内核是否支持该策略，插件是否依赖外网或未挂载的宿主文件 |
| `artifact_missing` / `archive_invalid` | 是否为没有共享归档的旧制品、归档是否完整；检查数据库和节点日志 |
| 一个节点失败，其他节点正常 | 比较节点系统、依赖、公钥、隔离配置和缓存目录权限 |
| 已启用但页面没有数据 | 是否为已授权的目录能力、是否登录、能力版本是否为 v1、返回值是否符合目录格式 |
| 操作返回代次冲突 | 刷新部署状态后再操作，避免多个管理员同时覆盖部署 |

管理 API 路径和参数见[接口速查](plugin-protocol-reference.md#管理接口)。
