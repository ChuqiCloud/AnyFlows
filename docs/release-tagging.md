# 版本标签规范

AnyFlows 的公开版本使用 [Semantic Versioning 2.0.0](https://semver.org/) 命名。标签统一以 `v` 开头，版本号只使用英文半角字符。

## 标签格式

| 类型 | 格式 | 用途 |
| --- | --- | --- |
| Alpha | `v主版本.次版本.修订号-alpha.序号` | 早期预览，接口、页面和配置仍可能调整 |
| Beta | `v主版本.次版本.修订号-beta.序号` | 功能测试与部署验证 |
| Release Candidate | `v主版本.次版本.修订号-rc.序号` | 发布候选版本，只处理阻塞发布的问题 |
| 正式版 | `v主版本.次版本.修订号` | 稳定发行版 |

示例：

```text
v0.3.0-alpha.1
v0.3.0-beta.1
v0.3.0-rc.1
v0.3.0
v0.3.1
```

预发布序号从 `1` 开始，同一阶段递增序号，进入下一阶段后重新从 `1` 开始。正式版发布后的修复版本递增修订号，如 `v0.3.1`，不再复用 `v0.3.0` 的预发布序列。

## 版本号含义

- **主版本号**：存在不兼容的 API、配置、数据库迁移或部署行为变更时递增。
- **次版本号**：增加向后兼容的功能时递增。
- **修订号**：只修复缺陷、调整文案或改进兼容性时递增。
- `0.y.z` 表示项目仍处于首个大版本之前；这一阶段的不兼容变更通过递增次版本号发布，并在发布说明中明确兼容范围。

预发布阶段使用 `alpha`、`beta`、`rc`。公开标签不使用其他阶段名称、日期、中文后缀或 `+build` 元数据；构建提交、来源版本和制品摘要写入发布说明及归档元数据。

标签创建后视为不可变引用。发现问题时创建新的序号或修订版本，不删除标签后复用同一个版本号。

## 社区版发布流程

发布内容通过 Gitea 导出流程同步到 GitHub：

1. 在 Gitea 完成版本更新和远程检查，将 `develop` 合并到 `master`。
2. 等待 GitHub 同步 PR 完成检查并合并到 `main`，核对版本和导出来源。
3. 分别在两个仓库对应的发布提交创建同名附注标签。导出流程重建 Git 历史，提交号可以不同；`docs/public-core-source.json` 记录 GitHub 内容对应的来源提交。
4. 向 GitHub 推送版本标签，触发 `Publish public release` 工作流。

同步 PR 合并不会自动创建 GitHub 标签或 Release。维护者须核对各仓库提交后单独推送标签，避免跨仓推送全部标签或私有历史。企业包由其独立交付流程管理。

## 发布检查清单

1. 确定本次发布阶段和下一个序号，确认没有复用已有标签。
2. 更新 workspace、内部依赖及 OpenAPI 版本。所有版本字段使用不带 `v` 的 SemVer。
3. 更新 `CHANGELOG.md`，说明迁移、配置和兼容性变化。
4. 将 Gitea `develop` 合并到 `master`，确认 GitHub `main` 已包含对应发布内容，并等待远程流水线完成。
5. 在正确仓库的发布提交上创建附注标签，推送前核对远程地址和标签指向。例如：

   ```bash
   git tag -a v0.3.0-rc.1 -m "AnyFlows v0.3.0-rc.1"
   git show --no-patch v0.3.0-rc.1
   ```

6. 向 GitHub 推送标签后，确认发布工作流成功、说明与 `CHANGELOG.md` 一致，并核对归档和 SHA-256 附件。工作流构建 Linux amd64 二进制及两套内置前端；Alpha、Beta 和 RC 标记为 Pre-release，正式版设为 Latest。

已公开的标签和 Release 产物不覆盖，修复后使用新的版本号。

标签校验由 [`tools/ci/verify-release-tag.sh`](../tools/ci/verify-release-tag.sh) 执行。它会拒绝缺少 `v`、阶段名称不在 `alpha`/`beta`/`rc` 中、序号为零或包含构建元数据的标签。
